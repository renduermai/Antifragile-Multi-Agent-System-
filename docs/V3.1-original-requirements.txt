# 反脆弱投资 Agent V3.1 系统开发需求

## 1. 项目目标

请使用Python开发一个基于多智能体的反脆弱投资研究与模拟决策系统，并通过Web前端展示分析结果。

本项目不是普通的股票分析工具，也不是自动交易机器人，而是一个能够主动观察世界、发现资产错价、识别潜在危机、推演极端情景，并结合真实期权价格寻找非对称收益机会的投资研究系统。

核心思想包括：

- 吸引子理论：识别资产长期价值锚、结构性力量及潜在的新均衡。
- 控制论：分析系统的正负反馈、关键约束、稳定状态与状态转移。
- 捕蝇草机制：持续积累独立信号，避免单一信号误触发，分级提升研究优先级。
- 反脆弱思想：寻找损失有限、潜在收益高度不对称的投资机会。
- 相对错价：寻找资产相对于合理参照体系的异常背离，并验证其经济解释与回归条件。
- 极端事件推演：主动寻找尚未发生、但可能迫使相关主体采取行动的重大事件，分析各方反应、产业网络瓶颈和价格传导。
- 赔率反推：根据真实期权成本，反推出交易所需要的最低联合成功概率，再检验现有证据是否支持。

最终实现以下闭环：

自动扫描 → 发现异常 → 新闻证据积累 → 矛盾识别 → 权力及产业网络分析 → 极端情景推演 → 时间与概率估计 → 期权赔率计算 → 分级预警 → 退出判断 → 历史验证与复盘。

## 2. 开发原则及范围限制

第一版只实现三个功能区：

1. 机会猎场：投资机会自动扫描、定向研究及持续追踪。
2. 案例区：历史案例存储、分轮盲测及验证。
3. 灵石区：API接口配置、连接测试及调用消耗。

不要擅自增加社交、用户注册、自动下单、复杂权限、多账户管理、投资组合交易平台等功能。

采用模块化设计，为未来扩展预留接口，但不要提前开发用户未要求的功能。

优先保证核心流程真正可运行、可验证、可维护，而不是追求功能数量和页面复杂程度。

所有计算必须尽量使用Python完成，不允许让大语言模型代替确定性数学计算。

## 3. 技术架构

建议技术栈：

- 后端：Python、FastAPI。
- Agent编排：LangGraph。
- 数据校验：Pydantic。
- 本地数据库：SQLite。
- 定时调度：APScheduler或其他轻量方案。
- 前端：简洁的HTML、CSS、JavaScript，可根据实际需求选择轻量框架，不引入不必要的复杂依赖。
- 配置：环境变量及独立配置文件。
- 测试：pytest。

第一版优先实现本地运行、数据持久化和浏览器访问。预留未来部署至云端的能力，但暂不实施复杂云部署。

API采用统一Provider接口，避免绑定单一供应商。

项目目录应按照数据采集、Agent、情景推演、期权计算、信号决策、风险控制、案例评测、数据库、API配置、前端及测试等模块划分。

## 4. 多Agent架构

保留A0至A12的13个逻辑模块，不要求每个逻辑模块都是一次独立LLM调用。功能相近的Agent可合并为同一个LangGraph节点，优先减少Token消耗。

A0：数据与证据管理Agent

负责新闻、行情、期权、宏观及产业数据的采集、去重、格式化、时间对齐和来源校验。

每条证据必须保存原文或允许保存的摘要、来源URL、事件发生时间、首次公开时间、系统获取时间及来源类型。

A1：机会扫描Agent

自动寻找价格异常、重大新闻事件、产业供需变化、历史极端状态及资金流异常，形成候选资产池。

支持从资产发现事件，也支持从事件反向发现相关资产。

A2：相对价值Agent

计算跨资产价格背离、滚动相关性、历史分位数、残差与均值回归条件。

不能把两条历史走势相似的曲线直接认定为具有必然回归关系。必须检查经济解释、数据口径、关系稳定性和结构突变。

A3：吸引子Agent

分析长期供需结构、政策制度、资本开支、货币信用、资金流向及技术变化，判断资产的主导定价力量是否发生迁移。

A4：新闻雷达与证据冲突Agent

不仅总结新闻，还要识别不同主体的声明、行动、立场变化和相互矛盾的证据。

重点区分公司公告、政府公告、媒体报道、当事人表态、市场传闻及模型推断。

特别关注具有影响力的主体在遭到另一主体明确拒绝后，是否仍然持续推进相关事件。

A5：产业网络Agent

识别供应链、运输航道、生产设施、资源加工、金融网络中的关键节点，分析节点受阻后的实际供需缺口、替代能力、恢复时间及受影响资产。

A6：博弈与权力结构Agent

识别事件中谁具有正式决定权、谁具有否决权、谁具有实际影响力。

构建多分支行动树，推演各参与方在不同条件下可能采取的行动、反制和缓解措施。

不得将可能发生的行动直接认定为必然发生。

A7：情景概率与时间Agent

分别建立基准、正向尾部、负向尾部及其他必要情景。

必须考虑事件是否发生、何时发生、何时公开、是否在期权到期前发生、发生后资产价格如何反应。

输出概率区间、估计依据、不确定性及可能导致改判的证据。无法合理估计时明确标记未知。

A8：反馈控制Agent

分析价格、资金、库存、产量、政策、流动性之间的正负反馈，识别系统处于稳定、临界、失稳、加速或恢复阶段。

A9：市场预期Agent

分析市场价格、期货期限结构、隐含波动率、期权偏斜、成交量及资金拥挤程度，判断相关风险是否已经被充分计价。

不能将风险中性概率直接当作真实事件发生概率。

A10：期权估值与赔率反推Agent

获取实际期权链报价，比较相同行权价的不同到期日，以及同一到期日的不同执行价。

使用Python计算每张成本、到期保本价、最大亏损、各情景收益、净期望收益及盈亏平衡概率。

将最低成功概率反向提供给A7，由A7检验现有独立证据是否支持该门槛。

为避免锚定偏差，A7必须先保存独立概率判断，再接收A10的赔率门槛；不得为了让交易通过而反复上调概率。

A11：风险、反证与退出Agent

主动寻找能够推翻投资假设的证据，识别时间风险、流动性风险、报价异常、期权归零风险及累计权利金消耗。

负责提出停止研究、禁止买入、停止加仓、减仓、平仓等模拟决策。

A12：评测与审计Agent

负责历史时点隔离、证据核验、计算校验、模拟成交审计、案例评分及失败原因归因。

不能使用事后结果反向修改已保存的事前判断。

## 5. Agent协作与信号规则

使用LangGraph实现条件路由，而不是所有Agent每次全部运行。

日常扫描时：

A0 → A1 → A2/A4 → 候选机会筛选。

只有发现值得研究的异常时，才启动：

A3/A5/A6 → A7/A8/A9 → A10 → A11 → 决策引擎 → A12审计。

按以下等级管理机会：

L0：日常观察。

L1：发现资产异常、结构变化或可信事件前兆。

L2：存在较明确的催化路径、现实约束或独立确认信号。

L2.5：尾部赔率候选。存在明确催化事件和时间窗口，获得可靠期权报价后，能够计算最低成功概率，但尚不足以证明交易优势。

L3：模拟买入候选。只有真实报价、保守情景下的净期望、期限、流动性、风险预算和反证检查均通过才能触发。

R1：过热、赔率下降或风险增加，停止追仓。

R2：催化事件兑现、核心驱动力减弱或交易优势消失，研究减仓及兑现收益。

R3：投资假设失效、到期风险或硬性风控触发，退出原模拟交易计划。

保留两条发现路径：

路径A：慢变量与资产重定价，例如黄金资金流、长期供给约束。

路径B：离散事件与极端冲击，例如地缘冲突、董事会决定、监管行动。

慢变量策略以周度确认和延迟执行稳健性检查为主；离散事件策略允许日内或事件驱动研究，不强制等待五个交易日，但必须单独验证真实执行条件。

信号阈值统一存放在配置文件中，记录规则版本。未经用户确认不得根据单个成功案例自动修改。

## 6. 核心期权计算要求

在完整情景模型下计算：

净期望收益 = 各情景概率 × 对应可实现收益之和 − 买入成本 − 交易费用。

在简化二元情景下计算：

盈亏平衡成功概率 =（总成本 − 失败情景剩余价值）÷（成功情景价值 − 失败情景剩余价值）。

明确区分：

- 事件发生概率。
- 事件在到期前发生的概率。
- 事件发生且资产价格产生足够变化的联合概率。
- 最终能够按目标价格成交退出的概率。

必须区分真实Bid、Ask、历史成交价、理论估值及模拟成交。

历史成交价不能直接冒充投资者可成交报价。

标准期权合约乘数默认100，但以实际合约数据为准。

如果缺少真实期权报价，可以展示理论估值和条件单研究方案，但必须标记为理论或假设，不得生成已成交记录，也不得据此触发L3。

## 7. 跨天记忆与事件持续追踪

这是第一版必须完成的核心功能。

系统每天运行时，不能像新开启一次聊天一样重新分析所有内容。

请建立持久化的事件档案，每个事件拥有唯一event_id，并保存：

- 关联资产及产业。
- 当前事件状态。
- 历史证据时间线。
- 已知事实、矛盾信息及待验证假设。
- 关键决策主体及权力关系。
- 当前情景及概率区间。
- 历史信号变化。
- 上一次分析的完整结构化结果。
- 下一次需要检查的关键信息。
- 期权历史报价及模拟决策。
- 使用的规则、Prompt和模型版本。

每次获取新新闻后，先判断该新闻属于已有事件还是新事件。

已有事件只分析新增信息：

1. 是否出现新事实？
2. 是否与旧事实矛盾？
3. 是否只是同一消息被转载？
4. 是否改变事件状态、概率、价格传导或期权赔率？
5. 是否需要升级、降级或关闭信号？

旧证据不能直接被新结论覆盖。系统需保留版本历史。

使用SQLite保存原始证据、结构化记忆、事件摘要及决策记录。LangGraph使用持久化Checkpoint或等效实现。

为节约Token，不要每次将所有历史新闻重新发送给模型。优先读取事件摘要、相关原文、近期增量及未解决的问题。

同时必须防止摘要遗漏重要反证；原始证据始终可以回溯。

跨天、重启服务后，系统仍应恢复原事件及此前判断。

## 8. 前端功能区一：机会猎场

这是系统首页。

页面保持简洁，主要展示：

顶部操作区：

- 开始全市场扫描。
- 输入资产代码或事件关键词，开始定向研究。
- 显示最近一次扫描时间、运行状态及是否开启定时扫描。

主要区域为机会列表，每个机会显示：

- 资产名称及代码。
- 当前价格或最近可用价格。
- 机会的一句话描述。
- 当前信号等级。
- 主要催化事件。
- 最大潜在风险。
- 期权赔率是否已验证。
- 首次发现日期及最新更新时间。

点击机会后展示详细报告：

- 关键新闻时间线与来源。
- 新增事实及与历史证据的矛盾。
- 相对错价及吸引子分析。
- 关键主体和产业网络。
- 极端情景行动树。
- 不同情景的概率、时间窗口和价格反应。
- 多期限期权比较及盈亏平衡概率。
- 第一人称模拟决策。
- 买入候选、退出条件和反证。
- 历史状态变化。

自动扫描不要求用户每次提供股票代码。

第一版先限定可配置的资产池，例如美股主要期权标的、黄金、原油、天然气、铜及主要股指ETF。

新闻扫描允许发现资产池之外的新候选，但需标记数据覆盖情况。

必须明确显示扫描范围，不能把有限资产池包装成已经覆盖全球全部市场。

定时功能默认关闭，用户可手动开启。开启后支持每日轻量新闻扫描、每周完整研究，以及对重点事件进行更高频率的可配置检查。

本地服务关闭期间不能假装仍在运行；重新启动后展示上一次成功扫描时间并支持增量补扫。

## 9. 前端功能区二：案例区

案例区是系统的独立历史测试环境，也是未来持续完善Agent的重要基础。

初始创建三个空案例档案：

- 黄金案例。
- 原油与霍尔木兹海峡案例。
- 英伟达NVDA案例。

不要自行编造三个案例的原文、历史行情或验证答案。

我会后续粘贴真实案例TXT和验证TXT。

每个案例包括两个相互隔离的内容区：

【案例TXT】

保存用户提供的案例背景、测试输入、历史时间节点及各轮新增事实。

支持粘贴文本、上传TXT、保存、编辑、运行。

系统根据TXT内容识别历史模拟时间和测试轮次；如果无法可靠识别，提示用户指定信息截断时间。

如果案例TXT包含完整事后结果，不能直接将全文发送给事前推演Agent。必须先按时间切分，无法安全切分时要求用户确认各轮内容。

支持单轮运行和按顺序执行下一轮。

例如英伟达案例可以依次模拟：

周五收盘前 → 周日新增消息 → 周一开盘 → 周一收盘后。

每轮只能读取当前及此前允许可见的信息，输出后保存完整决策快照，下一轮不能覆盖上一轮结果。

【验证TXT】

保存真实事件结果、真实行情、播客复盘、参考答案、评分标准等内容。

该内容仅允许A12评测模块在对应预测结果已锁定后访问，禁止传给正常研究、概率估计及期权选择Agent。

验证TXT可以包含真实结果和预期答案，但评测时应明确区分二者，不能因答案表达不同就判定事实错误。

点击“开始验证”后输出：

1. Agent找到了哪些关键证据。
2. 遗漏了哪些关键新闻和矛盾。
3. 哪些事实或数据错误。
4. 情景推演是否完整。
5. 概率和时间窗口是否合理。
6. 是否使用了未来信息。
7. 期权计算是否准确。
8. 模拟决策是否符合当时证据。
9. 实际行情是否符合预测情景。
10. 哪些环节需要改进，以及涉及哪个Agent。
11. 区分可实现收益、假设收益与真实成交收益。

验证结果显示分项评分、总体评价、具体差异及改进建议。

不得因为案例实际上涨就强行将此前空仓判定为错误。必须区分催化剂识别成功、买入条件成立、模拟执行成功和实际盈利。

每次案例运行保存独立run_id、模型版本和规则版本，允许比较不同版本的表现。

案例验证结论仅作为改进建议，不能自动修改生产规则或Prompt。

案例区与机会猎场的数据和记忆必须隔离。尤其不能将英伟达、原油、黄金的事后验证答案偷偷放进正常Agent的历史预测上下文。

历史检索仅允许使用模拟时点前已公开且可核实的证据。没有对应的历史新闻或行情数据时，明确标记无法验证，不得用当前网页内容冒充历史快照。

## 10. 前端功能区三：灵石区

所有外部API统一通过灵石区配置。

预留四类接口：

1. 大语言模型API：Base URL、API Key、Model Name。
2. 新闻与搜索API：Provider、Endpoint、API Key。
3. 金融行情API：Provider、Endpoint、API Key。
4. 期权数据API：Provider、Endpoint、API Key。

根据用户填写的服务进行配置，第一版优先实现OpenAI兼容的大模型接口，以及各数据类别至少一个实际可验证的Provider适配器。

不要声称一个通用URL和Key就能自动兼容所有数据服务。不同服务的鉴权和返回格式需要独立适配。

每类接口应支持：

- 保存配置。
- 测试连接。
- 显示配置状态和最近调用结果。
- 查看调用次数、Token用量及能够获得的费用估算。
- 设置单次运行和每日调用上限。
- 配置缺失时给出明确提示，并允许其他可运行模块继续工作。

API Key只允许在服务端使用，不得出现在前端日志、Agent输出、Git仓库或案例文件中。

前端保存后仅展示脱敏后的Key。Git忽略本地敏感配置文件。

未配置真实API时，允许使用明确标记的测试Fixture和Mock数据测试系统流程，但Mock数据不得进入真实投资机会榜单。

## 11. Token与运行成本控制

本项目需要长期运行，因此必须重视大模型调用成本。

原则：

- 行情计算、去重、规则判断、收益计算全部优先使用Python。
- 低价值新闻通过规则与关键词先过滤。
- 新闻结构化与简单分类使用低成本模型。
- 只有L1及以上候选才进入复杂分析。
- 深度模型集中用于因果推演、复杂矛盾、尾部情景及最终反证。
- 对已分析新闻进行缓存。
- 无实质新增信息时不重复运行完整Agent。
- 通过结构化JSON传递数据，避免多个Agent反复交换长篇文本。
- 限制单次分析中的模型调用次数、重试次数和上下文长度。
- 达到调用预算后停止低优先级分析，保留当前进度。

API缺失、预算耗尽、模型输出不合法时，系统应明确显示原因，而不是展示编造的投资结果。

## 13. 最终验收标准

第一版必须实际完成以下闭环：

1. 我在灵石区填写支持的API后，系统能够测试并调用真实接口。
2. 我不输入具体股票代码，系统能够在已配置的数据覆盖范围内自动发现候选事件及资产。
3. 我输入一个资产代码，系统能够生成完整且有证据来源的投资研究报告。
4. 第二天出现新增新闻后，系统能够回忆已有证据、历史判断并识别变化。
5. 服务重启后仍保留事件、信号和决策记录。
6. 系统能够正确计算期权成本、保本价、最大损失、情景收益及赔率门槛。
7. 缺少真实数据时，系统不会伪造报价、事实、来源或成交结果。
8. 我粘贴案例TXT后，能够按历史时点分轮展示Agent的决策过程。
9. 我粘贴验证TXT后，能够自动对照真实情况及参考答案，识别疏漏、错误和改进点。
10. 验证TXT及未来信息不会泄漏到事前推演模块。
11. 所有核心模块具有可运行测试，页面没有仅展示但无法操作的假功能。
12. 系统在限定预算下能够持续运行。
